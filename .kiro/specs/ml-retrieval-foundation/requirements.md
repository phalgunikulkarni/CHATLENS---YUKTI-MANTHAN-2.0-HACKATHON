# Requirements Document

## Introduction

This feature delivers the **ML/Retrieval foundation** for ChatLens, the AI-powered personal visual memory search engine ("You remember it. We find it."). It covers the smallest end-to-end slice that proves the core retrieval concept: turning a local image archive into searchable visual memories and returning ranked results for a natural-language query.

The scope is limited to four concrete deliverables:

1. **CLIP visual embeddings** for images.
2. **PaddleOCR text extraction** from images.
3. **ChromaDB vector index** for embedding storage and similarity search.
4. **Basic semantic image search** that ties CLIP + OCR + the vector index together, mapping a natural-language query to ranked image results.

This feature also includes the environment setup required for the ML/retrieval slice: installing only the Python packages needed for these four deliverables into the existing local virtual environment.

The mandatory technology stack is fixed by `docs/decisions.md`: OpenAI CLIP (visual embeddings), PaddleOCR (OCR), Sentence Transformers (text/semantic embeddings), ChromaDB (vector store), OpenCV + Pillow (image processing), Python 3.11. Any deviation from this stack must be recorded before implementation.

### Out of Scope (owned by teammates or later phases)

The following are explicitly **not** part of this feature and must not be implemented here:

- React frontend and search/chat UI.
- FastAPI backend API and request orchestration.
- Conversational Gemini intelligent agent and conversational refinement.
- Full "Why this result?" explainability presentation (this feature only retains the underlying signals; it does not build the user-facing explanation UI).
- Summarization and roadmap/plan generation actions.
- Google Calendar integration.
- SQLite FTS5 keyword search and full relational metadata store (part of the broader hybrid retrieval, but outside these four immediate deliverables).

### Strict Scope Constraints

The following hard constraints govern what this feature may create and implement:

- No sample, random, or placeholder files or datasets shall be generated by this feature; no `data/` directory or sample images shall be created.
- No new top-level directories shall be created outside the existing `ml/` directory; specifically no `frontend/`, `backend/`, or `ai/` folders.
- The feature MAY READ from a developer-supplied dataset directory (for example `data/test_dataset/`) that already exists in the repository; reading an externally provided dataset is permitted, while generating, downloading, or synthesizing dataset files remains prohibited.
- No assumptions or scaffolding beyond the four deliverables (CLIP visual embeddings, PaddleOCR text extraction, ChromaDB vector index, basic semantic image search) and their environment setup shall be introduced.
- All code and artifacts shall live within the existing `ml/` directory only.
- The Local_Dataset is supplied externally by the developer at run time; the feature reads from a provided path and never fabricates or generates image files.

### Data Integrity Constraint

A locally collected or imported image dataset is acceptable for this prototype. The system MUST NOT fabricate personal history, viewing history, timestamps, or any metadata that does not genuinely exist for an image. Only metadata that actually exists (for example, filename and file path) may be stored.

## Glossary

- **ML_Retrieval_System**: The overall ML/retrieval component built by this feature, comprising the embedder, OCR extractor, vector index, and search modules. Resides in the repository `ml/` directory.
- **Image_Embedder**: The component that generates CLIP visual embeddings from image files.
- **Text_Embedder**: The component that generates text embeddings using Sentence Transformers, used to embed natural-language queries and OCR text into a comparable semantic space.
- **OCR_Extractor**: The component that extracts text from images using PaddleOCR.
- **Vector_Index**: The ChromaDB-backed component that stores embeddings and performs similarity search.
- **Search_Module**: The component that accepts a natural-language query and returns ranked image results by combining CLIP, OCR, and the Vector_Index.
- **Ingestion_Pipeline**: The process that reads images from a local dataset directory, runs OCR and embedding, and writes records into the Vector_Index.
- **Image_Record**: The stored unit for one image, containing an image identifier, file path, OCR text, embedding reference(s), and retrieval signal data.
- **Retrieval_Signal**: A per-result piece of evidence describing why a result was retrieved (for example, visual similarity score, semantic OCR similarity score, matched OCR terms).
- **Local_Dataset**: A directory of image files on the local filesystem used for prototyping.
- **Ranked_Result**: A single search result containing the image identifier, file path, an overall relevance score, and the associated Retrieval_Signals.
- **Environment**: The Python 3.11 virtual environment (`.venv`) at the workspace root into which task dependencies are installed.

## Requirements

### Requirement 1: Environment and Dependency Setup

**User Story:** As a developer on the ML/retrieval slice, I want the required packages installed into the existing local virtual environment, so that I can run CLIP, PaddleOCR, Sentence Transformers, and ChromaDB without setup errors.

#### Acceptance Criteria

1. THE ML_Retrieval_System SHALL declare its Python dependencies in a dependency manifest file within the `ml/` directory.
2. THE dependency manifest SHALL include only the six mandatory-stack packages — OpenAI CLIP, PaddleOCR, Sentence Transformers, ChromaDB, OpenCV, and Pillow — together with their transitive supporting libraries, and no other top-level packages.
3. WHERE a top-level package not listed in the mandatory stack defined in `docs/decisions.md` is added to the dependency manifest, THE ML_Retrieval_System SHALL record the package name and a written justification in project documentation before the package is used.
4. WHEN the documented installation command is run against the existing Python 3.11 virtual environment at the workspace root, THE ML_Retrieval_System SHALL complete installation with a success (zero) exit status and make all six mandatory-stack packages resolvable in that environment.
5. WHEN the verification script is run after installation, THE ML_Retrieval_System SHALL import OpenAI CLIP, PaddleOCR, Sentence Transformers, ChromaDB, OpenCV, and Pillow, emit one pass/fail result line per package, and report an overall success indication only when all six imports succeed.
6. IF a mandatory-stack dependency fails to install or import, THEN THE ML_Retrieval_System SHALL report the name of the failing dependency together with its associated error message and terminate with a non-success (non-zero) completion status.

### Requirement 2: Local Image Ingestion

**User Story:** As a developer, I want to load images from a local dataset directory, so that they can be processed into searchable visual memories.

#### Acceptance Criteria

1. WHEN a Local_Dataset directory path is provided, THE Ingestion_Pipeline SHALL recursively enumerate the supported image files contained in that directory and all of its subdirectories.
2. THE Ingestion_Pipeline SHALL treat files with the extensions PNG, JPG, JPEG, and WEBP as supported, matching extensions case-insensitively.
3. THE Ingestion_Pipeline SHALL ignore hidden and system files (for example, dotfiles such as `.DS_Store`) and SHALL NOT emit records for them.
4. WHEN an image file is discovered, THE Ingestion_Pipeline SHALL produce a structured record containing at minimum a stable image identifier, the image file path, the filename, and a category.
5. THE Ingestion_Pipeline SHALL derive the category for an image from the name of the immediate parent folder containing that image.
6. WHEN an image file is read, THE Ingestion_Pipeline SHALL assign a stable image identifier deterministically derived from the image file path such that the same path always yields the same identifier.
7. THE Ingestion_Pipeline SHALL store only metadata that genuinely exists (image identifier, file path, filename, and folder-derived category) and SHALL NOT fabricate timestamps, personal history, or any unavailable metadata.
8. THE Ingestion_Pipeline SHALL NOT modify, move, rename, or write to any scanned image file.
9. IF the provided Local_Dataset directory path does not exist or cannot be read, THEN THE Ingestion_Pipeline SHALL report an error indicating the directory is missing or unreadable and SHALL NOT process any images.
10. WHEN scanning completes, THE Ingestion_Pipeline SHALL report the count of discovered images and the count of ignored/skipped files, reporting zero discovered images when the directory contains no supported image files.

### Requirement 3: CLIP Visual Embeddings

**User Story:** As a developer, I want each image converted into a CLIP visual embedding, so that images can be matched by visual and semantic similarity.

#### Acceptance Criteria

1. WHEN an image that has been successfully decoded and contains non-zero pixel data is provided, THE Image_Embedder SHALL generate a CLIP visual embedding vector for that image.
2. THE Image_Embedder SHALL produce visual embedding vectors of an identical fixed length for every image processed under the same model configuration.
3. WHEN a natural-language query is provided, THE Image_Embedder SHALL generate a CLIP text embedding whose vector length is identical to the visual embedding length, so that text and image embeddings can be compared by similarity in the same vector space.
4. THE Image_Embedder SHALL load the CLIP model exactly once per process and reuse the loaded model for all subsequent embedding calls within that process.
5. IF an image cannot be decoded or contains no pixel data, THEN THE Image_Embedder SHALL reject that image, report the image identifier together with an error indication, generate no embedding for it, and continue processing the remaining images.
6. IF visual embedding generation fails for a decoded image, THEN THE Image_Embedder SHALL report the image identifier together with an error indication, store no embedding for that image, and continue processing the remaining images.
7.If a visual embedding is not generated for a particular image(new image),the model has to automatically embed using CLIP model.

### Requirement 4: OCR Text Extraction

**User Story:** As a developer, I want text extracted from each image, so that screenshots, notes, and documents can be matched by their textual content.

#### Acceptance Criteria

1. WHEN an image in a supported format (PNG, JPG, or JPEG) is provided, THE OCR_Extractor SHALL extract text content from the image using PaddleOCR and associate the extracted text with the image identifier of the source image.
2. WHEN an image contains no detectable text, THE OCR_Extractor SHALL return an empty string as the text result associated with the image identifier and SHALL treat the extraction as successful rather than returning an error.
3. THE OCR_Extractor SHALL load the PaddleOCR model once per process and reuse the loaded model across all subsequent extraction calls within that process.
4. IF the PaddleOCR model fails to load, THEN THE OCR_Extractor SHALL report an error indicating that model initialization failed and SHALL NOT attempt text extraction.
5. IF a provided image is not in a supported format (PNG, JPG, or JPEG), THEN THE OCR_Extractor SHALL reject the image, report the image identifier and an error indicating the format is unsupported, and SHALL allow processing of remaining images to continue.
6. IF text extraction for an image does not complete within 30 seconds, THEN THE OCR_Extractor SHALL abort extraction for that image, report the image identifier and an error indicating a timeout, and SHALL allow processing of remaining images to continue.
7. IF text extraction fails for an image, THEN THE OCR_Extractor SHALL report the image identifier and an error indication, SHALL NOT emit a partial or corrupt text result for that image, and SHALL allow processing of remaining images to continue.

### Requirement 5: Vector Index Storage and Similarity Search

**User Story:** As a developer, I want embeddings stored in a persistent vector index that supports similarity search, so that queries can retrieve the most relevant images efficiently.

#### Acceptance Criteria

1. WHEN an Image_Record with its embedding is provided, THE Vector_Index SHALL store the embedding together with the image identifier and the associated metadata in ChromaDB.
2. THE Vector_Index SHALL persist stored records to the local filesystem so that stored embeddings remain available across separate process runs.
3. WHEN a query embedding and a result count N between 1 and 100 are provided, THE Vector_Index SHALL return at most N stored records ordered by descending similarity to the query embedding.
4. WHEN the Vector_Index returns a record, THE Vector_Index SHALL include the image identifier, the stored metadata, and a similarity score between 0.0 and 1.0 for that record.
5. WHEN an image identifier that already exists in the Vector_Index is stored again, THE Vector_Index SHALL update the existing record rather than create a duplicate record.
6. IF a similarity search is requested WHILE the Vector_Index contains no records, THEN THE Vector_Index SHALL return an empty result set without error.
7. IF a provided query embedding has a length different from the stored embedding length, THEN THE Vector_Index SHALL return an error indicating a dimensionality mismatch and SHALL NOT return results.
8. IF the provided result count N is less than 1 or greater than 100, THEN THE Vector_Index SHALL return an error indicating N is outside the accepted range and SHALL NOT return results.
9. WHEN fewer than N stored records exist, THE Vector_Index SHALL return all stored records ordered by descending similarity.

### Requirement 6: Basic Semantic Image Search

**User Story:** As a user, I want to describe what I remember about an image in natural language and get back a ranked list of matching images, so that I can find a visual memory without knowing its filename.

#### Acceptance Criteria

1. WHEN a non-empty natural-language query of up to 1,000 characters and a result count N between 1 and 100 are provided, THE Search_Module SHALL return a set of Ranked_Results containing at most N entries, ordered by descending overall relevance score.
2. THE Search_Module SHALL combine a visual similarity signal from CLIP query-to-image matching and a semantic text similarity signal from Text_Embedder matching between the query and stored OCR text when computing the overall relevance score used for ordering.
3. WHEN a Ranked_Result is produced, THE Search_Module SHALL include the image identifier, the image file path, an overall relevance score between 0.0 and 1.0, and the list of Retrieval_Signals that contributed to the result.
4. WHEN a query matches OCR text of an image, THE Search_Module SHALL include the matched OCR terms as a Retrieval_Signal for that result.
5. WHEN fewer than N images in the Vector_Index produce a non-zero relevance score for a query, THE Search_Module SHALL return only the matching images ordered by descending overall relevance score.
6. IF a query is submitted WHILE the Vector_Index contains zero records, THEN THE Search_Module SHALL return an empty result set and include an indication that no images are indexed.
7. IF a query is empty or contains only whitespace, THEN THE Search_Module SHALL return no results, leave the Vector_Index unchanged, and return an error indication that a non-empty query is required.
8. IF the provided result count N is less than 1 or greater than 100, THEN THE Search_Module SHALL return no results, leave the Vector_Index unchanged, and return an error indication that N is outside the accepted range.

### Requirement 7: Retrieval Signal Retention for Explainability

**User Story:** As a developer building toward the "Why this result?" feature, I want each result to retain the signals that caused it to be retrieved, so that a later phase can explain results using genuine evidence.

#### Acceptance Criteria

1. WHERE visual similarity contributed to a Ranked_Result, WHEN the Search_Module produces that Ranked_Result, THE Search_Module SHALL attach the numeric visual similarity score used for that result as a normalized value between 0.0 and 1.0 inclusive.
2. WHERE semantic OCR similarity contributed to a Ranked_Result, WHEN the Search_Module produces that Ranked_Result, THE Search_Module SHALL attach the numeric semantic OCR similarity score used for that result as a normalized value between 0.0 and 1.0 inclusive.
3. WHERE OCR term matches contributed to a Ranked_Result, WHEN the Search_Module produces that Ranked_Result, THE Search_Module SHALL attach the specific matched terms, up to a maximum of 100 terms, as a Retrieval_Signal.
4. IF a candidate signal type did not contribute to a Ranked_Result, THEN THE Search_Module SHALL NOT attach a Retrieval_Signal of that type to the result.
5. THE Search_Module SHALL attach a Retrieval_Signal to a Ranked_Result only when that signal corresponds one-to-one to a value produced by an actual retrieval computation for that result.

### Requirement 8: Module Structure and Loose Coupling

**User Story:** As a team member working on other components, I want the ML/retrieval code organized into separable modules with clear interfaces, so that ingestion, OCR, embeddings, and retrieval can evolve independently.

#### Acceptance Criteria

1. THE ML_Retrieval_System SHALL place its code within the repository `ml/` directory as four separate modules for ingestion, OCR, embeddings, and retrieval, where each module resides in its own directory located directly under `ml/` rather than nested inside another module's directory.
2. THE Image_Embedder, OCR_Extractor, Vector_Index, and Search_Module SHALL each expose a callable interface that can be imported and invoked without importing or initializing any of the other three components.
3. THE Search_Module SHALL invoke the Image_Embedder, OCR_Extractor, and Vector_Index only through their exposed callable interfaces and SHALL NOT access their internal definitions directly.
4. WHERE the `ml/` directory contains pre-existing nested folders that do not match the four-module layout defined in criterion 1 (for example `ml/ocr/embeddings/retrieval/ranking`), THE ML_Retrieval_System SHALL place new code in the four top-level module directories and SHALL NOT place new code inside those pre-existing nested folders.

### Requirement 9: Strict Scope and No-Fabrication Enforcement

**User Story:** As a team lead coordinating multiple contributors, I want the ML/retrieval feature to stay strictly within its assigned scope and never fabricate files or datasets, so that the repository structure and other teammates' work remain undisturbed.

#### Acceptance Criteria

1. THE ML_Retrieval_System SHALL create files and directories only within the existing `ml/` directory and SHALL NOT create any `frontend/`, `backend/`, `ai/`, or `data/` directory.
2. THE ML_Retrieval_System SHALL NOT generate, download, or synthesize sample images, placeholder datasets, or random test files.
3. WHERE an image dataset is required, THE ML_Retrieval_System SHALL read images only from a Local_Dataset path explicitly provided by the developer at run time and SHALL NOT create that dataset.
4. THE ML_Retrieval_System SHALL implement only the four in-scope deliverables — CLIP visual embeddings, PaddleOCR text extraction, ChromaDB vector index, and basic semantic image search — together with their environment setup, and SHALL NOT implement any feature listed in the Out of Scope subsection.
5. WHERE functionality beyond the four deliverables appears necessary, THE ML_Retrieval_System SHALL surface that functionality as a note for team discussion rather than implement it.
